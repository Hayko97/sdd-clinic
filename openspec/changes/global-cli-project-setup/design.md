# Design

## Context and decisions
Use a thin global launcher backed by the Docker runtime. Package the runtime assets needed to start the matching version from any working directory; do not depend on the caller being inside Clinic's source checkout. Support local package installation for development and verification; publishing requires a separate request.

Retain `sdd-clinic` and add `sddclinic`. Reuse the setup orchestration and proposal validation/application services behind a container-side terminal runner. Do not duplicate baseline analysis or bypass authenticated browser endpoints through unauthenticated HTTP additions. Provider protocols remain in existing adapters.

The launcher resolves the target path and passes it as an argument and an explicit Docker mount, without shell interpolation. Use dedicated terminal-runtime Compose identity/state so an arbitrary setup invocation cannot replace the browser runtime's /projects mount. Terminal run history remains separate, but every successfully configured project must be registered in the global GUI with access to its repository. Persist container provider credentials in private runtime state. Resolve provider choice from existing project configuration or prompt when absent. Missing authentication produces provider-specific container sign-in instructions without copying host credentials or silently switching engines.

Review inventories existing .clinic agent definitions, schedules/configuration, canonical skills, tool entrypoints, instructions, accepted specs and active changes. Reuse the existing source scanner and report exclusions; preserve custom definitions verbatim. Explain gaps and contradictions without automatically rewriting customized agent policy. Guidance-only mode performs local inventory and scaffolding but explicitly reports that semantic code analysis was not run.

## Interfaces and data
Proposed surface: `sddclinic setup [path] [--engine codex|claude] [--guidance-only] [--model MODEL] [--reasoning EFFORT]`. Default path is cwd. Show progress and a coverage/asset summary, allow inspection of the entire diff, then ask to apply. No implicit yes and no --yes shortcut in this slice. Noninteractive invocation fails before model analysis or mutation with instructions to use an interactive terminal. Exit 0 for completed setup/no changes, 1 for failure, 2 for invalid invocation/prerequisites, and 130 for cancellation. Declining application exits successfully with an explicit not-applied message.

Validate target directory, Docker availability and runtime compatibility first. Target source changes or stale output reject the whole proposal. Treat SIGINT as cancellation and retain diagnostics without applying partial setup. Add an optional setup profile to portable project configuration and resolved model/effort metadata to setup run evidence; existing configurations remain valid. This document is the CLI contract; separate contracts.md/data-model.md files are unnecessary. Update the existing installation guide as the walkthrough after implementation.

## Risks and rollout
Container path translation, permission ownership, spaces in paths and coexisting browser mounts require process-level tests. Large projects can exceed existing scanner/model limits; report failure without completeness claims. Existing ignored specs or agent files must be reported as excluded rather than silently claimed analyzed. Validate packed runtime assets and aliases in a clean installation prefix. Installation must not launch services or modify a project until the user runs setup. Scope is local macOS/Linux and WSL with Docker; native Windows support is not added.

## Model and reasoning selection
Before full analysis, resolve the selected engine, enumerate supported models/effort controls where the runtime supports discovery, and show a terminal model selector. For Codex, recommend `gpt-6.1-sol` with explicit `medium` when available. Precedence is explicit flags, then the displayed and confirmed setup profile, then the recommended pair. Ordinary Developer/QA/PO settings and provider-global effort are not setup defaults. A saved setup profile above medium must require renewed explicit selection on each run; never start at xhigh/max merely because it was saved or inherited. No automatic escalation based on repository size or retries.

Keep model and effort distinct. Reject unsupported pairs before inference; when availability cannot be established, explain the uncertainty and request a supported selection rather than silently falling back. A provider rejection fails visibly without changing model or effort. Claude uses its own runtime-supported model identifiers and a verified moderate effort option; if the installed adapter cannot enforce that option, report the limitation and require runtime/adapter support before full analysis. Guidance-only mode needs neither model selection nor authentication and rejects inference-only flags as incompatible.

Resolve one pair for the setup run and forward it to every analysis, consolidation and synthesis request. Extend adapter inputs with explicit reasoning effort and validate provider-specific encoding against the packaged CLI protocol. Do not assume a Responses API parameter is accepted by app-server. Record the selected pair and source in run evidence; show the effective selection before analysis. Include a setup-specific profile in the final reviewed .clinic/project.yaml proposal, preserving existing agent models and unrelated configuration. If a custom setup profile already exists, changes appear explicitly in that diff. Declining setup leaves repository configuration unchanged. A fresh run after profile changes must not mislabel old model evidence as new.

Recommend medium as a research-backed starting point, with optional opt-in evaluation on small, mixed and large repositories comparing Sol medium with Luna medium and Sol high where supported. Compare coverage, citation validity, contradictions, useful proposals, latency and token usage; fixture tests verify configuration enforcement, not semantic model quality. Do not advertise a measured optimum without those results.

## Global GUI registration
Owner clarification during implementation: setup projects must appear in the global SDD Clinic GUI. This supersedes the earlier separate-registration assumption; prior QA does not verify this added behavior.

Maintain a host-local global GUI descriptor and durable registration manifest outside project repositories. The source installer attaches to its existing Compose GUI when present; otherwise use a packaged persistent global GUI service. Successful setup records a durable completion receipt in terminal state. The host reads that receipt, records the canonical project path and uses stable container mounts under /clinic-projects/<path-hash> when the project is not already covered by an existing bind mount. Existing mounts and registration paths remain intact. Add mounts with a generated Compose override; do not expose the whole host filesystem.

Register through the GUI runtime's existing Projects service and local Store so its project-card home and workspace use the same repository data. Repeated setup resolves the existing registration. When a new mount requires service recreation, check for active or review-waiting runs first. If busy or unavailable, keep pending registration in the manifest, report setup success and GUI registration pending separately, and let `sddclinic start` retry without requiring analysis or application again. Do not claim GUI visibility until registration and directory access succeed. Launch the GUI through `sddclinic start`, using its managed mounts/descriptor; preserve start port/data-dir/no-open options. Starting a stopped GUI and adding mounts are within the requested local setup workflow; never interrupt active work automatically.
